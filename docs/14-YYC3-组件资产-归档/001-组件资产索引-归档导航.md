## 一、归档目的

把「历史资产（docs/packages）」与「当前项目组件（packages/）」放到同一张地图上，回答三个问题：

1. 有哪些组件、分别在哪、是否可用；
2. 哪些只是占位、缺口在哪；
3. 下一批按什么顺序接入业务页面。

## 三、完成度判定口径（强制）

| 状态 | 定义 | 判定证据 |
| ------ | ------ | ---------- |
| **完整** | 有真实数据来源、有交互、有异常分支、有测试 | 页面无硬编码指标；组件有单测或 E2E |
| **可用** | 结构完整、交互可用，数据为本地/mock | 可操作，但数据未接后端 |
| **骨架** | 仅布局与静态文案，无状态 | 无 `useState`/事件处理 |
| **占位** | 路由存在但渲染空或 TODO | `routes: []`、`() => null` |

> 归档表中的「状态」必须与上述口径一致；升级状态时同步更新台账（docs/13）。

## 四、资产分层与迁移原则

```
历史资产 docs/packages/**           当前工程 packages/**
  @yyc3/ui      ──迁移──▶  packages/ui        （已启用，49 基础件 + 品牌件）
  @yyc3/theme   ──迁移──▶  packages/theme     （已启用，CSS 变量 + @theme 映射）
  @yyc3/ai-family（40+ 组件/8 store slice）── 待评估，按组件逐个移植
  @yyc3/core / store / business            ── 待评估，避免引入第二套状态栈
```

**原则**：一次只迁一个组件，迁移即补类型、补测试、补状态标记；不整包搬运。

## 五、接入顺序（迭代计划）

| 阶段 | 内容 | 验收 |
| ------ | ------ | ------ |
| M1（已完成） | `packages/ui` + `packages/theme` 启用；`/design` 设计系统页；`/family` AI Family 工作台骨架 | 构建通过、截图核对、E2E 13/13 |
| M2 | AI Family 四视图接真实数据：成员状态、技能列表、会话存储 | 无 mock 文案；有单测 |
| M3 | 4 个业务引擎页面（目标/成本/营销/提示词）复用 `/design` 组件 | 每页 1 条 E2E |
| M4 | 历史 `ai-family` 组件按需移植（音乐/情感/语音） | 每个组件独立 PR |
